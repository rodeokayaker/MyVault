# Apex-домен недоступен у части пользователей (2026-06-08)

## Резюме

Часть посетителей не может открыть сайт — получают `ERR_TIMED_OUT`. У большинства — работает. Корневая причина: **у этих пользователей фильтруется apex-домен `kayakmoscow.ru`** (без `www`) на уровне их провайдера/DNS, а `www.kayakmoscow.ru` проходит.

Сделаны 3 серверные правки, снижающие вероятность попадания в проблему. Финальный фикс требует тикета хостеру (упрощение nginx-конфига) и настройки в Яндекс.Вебмастере (главное зеркало www).

## Симптомы (как обнаружили)

Пользователь прислал:
- Скриншот: `kayakmoscow.ru` в Яндекс.Браузере, ошибка «Не удаётся установить соединение», `ERR_TIMED_OUT`.
- Аудио-разъяснения (расшифровано):
  - «По ссылке из WhatsApp перешёл — работает. А из Яндекс-поиска в любом браузере — белая страница».
  - «Скопировал ту же ссылку из WhatsApp, отправил в Telegram, потом в Max — ни откуда не открывается».
  - «**С VPN и без VPN — одинаково**, ни хрена не получилось».
  - «Когда вбил руками `www.kayakmoscow.ru` — открылось во всех браузерах (Safari, Opera, Яндекс)».

«Не первый случай» — проблема повторяющаяся, но точечная (у конкретных пользователей).

## Диагностика — что отметали

| Гипотеза | Почему отмели |
|---|---|
| Сайт упал | curl с моей машины: HTTP 200, всё работает |
| IP-блок shared-хостинга РКН | VPN не помогает — значит не TCP-блок IP |
| Проблема Яндекс.Браузера | Пользователь пробовал «в любом из браузеров» — везде то же |
| Реклама/блокировщики/расширения | Не объясняет «копию ссылки в Telegram/Max тоже не открыть» |
| Поломанный DNS на устройстве | Возможно, но `www.kayakmoscow.ru` резолвится нормально → не системный DNS |

## Корневая причина

**Apex-хост `kayakmoscow.ru` (без www) недоступен у этого пользователя**, а `www.kayakmoscow.ru` — доступен.

Подтверждающие наблюдения:
- Прямой ввод `www.kayakmoscow.ru` → работает везде.
- Все «не открывающиеся» переходы шли по `kayakmoscow.ru` (без `www`): Яндекс-поиск выдаёт ссылки на apex, Telegram/Max в превью отбрасывают `www`.
- WhatsApp-ссылка содержала `www.` явно — поэтому работала.

Вероятный механизм блокировки apex (один из):
1. **DPI у провайдера фильтрует по SNI=`kayakmoscow.ru`**. Шаред-хостинг 4thplace.ru — у соседей по IP кто-то мог попасть в реестр РКН, фильтр срабатывает на конкретный hostname.
2. **DNS-фильтр у пользователя** (AdGuard DNS, NextDNS, или роутер) режет apex но не www.

VPN не помог скорее всего потому, что у пользователя «VPN» — браузерное расширение, а не системный профиль (заявил «не работает в любом браузере» — значит VPN был только в одном).

## Почему редиректы добивали ситуацию

Цепочка `http://kayakmoscow.ru/` через `curl -L`:

```
http://kayakmoscow.ru/      → 301 → https://kayakmoscow.ru:443/    (apex HTTPS)
https://kayakmoscow.ru:443/ → 301 → https://www.kayakmoscow.ru/    (apex→www)
https://www.kayakmoscow.ru/ → 200
```

**Каждый из первых двух хопов содержит apex-хост** (в HTTP-Host или TLS-SNI). Если фильтр режет apex — ни один из этих хопов не доходит до сервера, пользователь видит `ERR_TIMED_OUT` ещё до того, как сервер успевает редиректнуть.

`Strict-Transport-Security` (HSTS) **не был выставлен** ни на одном варианте.

## Что выкатил на сервере (2026-06-08)

### Правка 1 — JSON-LD logo в шаблоне Bitrix

Файл: `~/www/kayakmoscow.ru/local/templates/kayak-moscow/header.php`, строка 75.

```diff
-  "logo": "https://kayakmoscow.ru/bitrix/images/logo1.jpg",
+  "logo": "https://www.kayakmoscow.ru/bitrix/images/logo1.jpg",
```

Единственная захардкоженная apex-ссылка в шаблоне. Подавала противоречивый сигнал поисковикам (canonical везде www, а logo — apex). После правки JSON-LD согласован с canonical.

Бэкап: `header.php.bak-20260608`.

### Правка 2 — HSTS через панель ISPmanager

В `webdomain.edit` для `kayakmoscow.ru` поле `hsts` переключено с `off` → `on`.

После этого nginx добавляет на все HTTPS-ответы:

```
Strict-Transport-Security: max-age=31536000;
```

Заголовок приходит и на финальной странице www, и на промежуточном 301-редиректе с apex HTTPS. После первого успешного визита по `https://www.kayakmoscow.ru/` браузер на год запомнит обязательность HTTPS — лишний хоп `http://www` исчезнет.

⚠️ Шаблон ISPmanager ставит **только `max-age`**, без `includeSubDomains; preload`. Для подачи в HSTS Preload List этого недостаточно (см. ниже про тикет хостеру).

### Правка 3 (откачена) — HSTS через .htaccess

Промежуточная попытка добавить HSTS через `.htaccess` (`mod_headers`). Сработала, но после включения HSTS в панели создавала **дубль заголовка** на `https://www`. Откатан до `.htaccess.bak-20260608`.

## Smoke-тест после правок

```
https://www.kayakmoscow.ru/  → 200, 1× Strict-Transport-Security, canonical=www, logo=www
https://kayakmoscow.ru/      → 301, Strict-Transport-Security присутствует, Location=www
/, /calendar/, /sup/, /contacts/, /events/  → все 200
```

## Что осталось — нужны внешние действия

### A. Тикет хостеру 4thplace.ru (главное)

В nginx-шаблоне нужно:
1. Сократить цепочку `http://kayakmoscow.ru → https://kayakmoscow.ru:443 → https://www.kayakmoscow.ru` до **одного хопа** `http → https://www`.
2. Расширить HSTS до `max-age=63072000; includeSubDomains; preload` (Preload-совместимый).
3. Разместить правки так, чтобы их не затирало при следующем сохранении настроек через ISPmanager.

Готовый текст тикета — в разделе «Тикет хостеру» ниже.

### B. Яндекс.Вебмастер — главное зеркало www

Зайти в [webmaster.yandex.ru](https://webmaster.yandex.ru/) → `kayakmoscow.ru` → «Индексирование» → «Переезд сайта» → указать главное зеркало `www.kayakmoscow.ru`. После этого Яндекс перестанет показывать apex-URL в выдаче — пользователи будут попадать сразу на www.

### C. HSTS Preload (после пункта A)

После выполнения пункта A — подать заявку на [hstspreload.org](https://hstspreload.org). Домен попадёт во встроенный whitelist Chrome/Safari/Firefox/Edge, и все эти браузеры **никогда** не сделают HTTP-запросов к `kayakmoscow.ru` → проблема с цепочкой редиректов исчезнет окончательно.

### D. Опционально — смена shared-IP

Если хостер откажет по пунктам A или попросит денег — отдельным тикетом запросить смену shared-IP с обоснованием «у части пользователей домен фильтруется, предположительно из-за соседа по IP в реестре РКН». Обычно делают бесплатно.

## Тикет хостеру (готовый текст)

> **Тема:** Оптимизация HTTP-редиректов и HSTS для сайта kayakmoscow.ru (логин `kayaking`)
>
> Здравствуйте.
>
> Прошу настроить nginx-конфигурацию для сайта `kayakmoscow.ru` (аккаунт `kayaking`).
>
> **1. Сократить цепочку HTTPS-редиректов до одного хопа.** Сейчас при заходе на `http://kayakmoscow.ru/` происходит 3 редиректа:
>
> ```
> http://kayakmoscow.ru/      → 301 → https://kayakmoscow.ru:443/
> https://kayakmoscow.ru:443/ → 301 → https://www.kayakmoscow.ru/
> https://www.kayakmoscow.ru/ → 200
> ```
>
> Промежуточный хоп через `https://kayakmoscow.ru:443/` создаёт проблему: у части пользователей (например, с провайдерами, где работает фильтрация по SNI/Host) запрос с `Host: kayakmoscow.ru` блокируется на TCP-уровне, и они получают `ERR_TIMED_OUT`. Прошу настроить, чтобы все варианты входа сразу одним 301 шли на `https://www.kayakmoscow.ru$request_uri`.
>
> ```nginx
> server {
>     listen 80;
>     server_name kayakmoscow.ru www.kayakmoscow.ru;
>     return 301 https://www.kayakmoscow.ru$request_uri;
> }
> server {
>     listen 443 ssl http2;
>     server_name kayakmoscow.ru;
>     # ... ssl_certificate / ssl_certificate_key как сейчас ...
>     add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;
>     return 301 https://www.kayakmoscow.ru$request_uri;
> }
> ```
>
> **2. Расширить HSTS до Preload-совместимого варианта.** Сейчас nginx отдаёт `Strict-Transport-Security: max-age=31536000;` (HSTS включил через панель). Прошу заменить на:
>
> ```nginx
> add_header Strict-Transport-Security "max-age=63072000; includeSubDomains; preload" always;
> ```
>
> Это нужно для подачи заявки в [hstspreload.org](https://hstspreload.org) — после принятия домен попадёт во встроенный whitelist Chrome/Safari/Firefox/Edge.
>
> **3. Сохранение при последующих правках через ISPmanager.** Прошу разместить изменения так, чтобы их не затёрло при следующем сохранении настроек домена через панель (no-regen секция или приоритетный include).
>
> Спасибо!

## Технические наблюдения и заметки

### Файлы сайта

Webroot: `/var/www/kayaking/data/www/kayakmoscow.ru/` (= `~/www/kayakmoscow.ru/`).
Активный шаблон Bitrix: `local/templates/kayak-moscow/`.

### Canonical, sitemap, robots — уже корректны (сделано в прошлых сессиях)

- `<link rel="canonical" href="https://www.kayakmoscow.ru/...">` есть на всех 20+ проверенных страницах. Код в `header.php:46-67`, корректно исключает 404 и `/calendar/detail.php`.
- `sitemap.xml` + sub-sitemaps — все URL на `www.`.
- `robots.txt` → `Sitemap: https://www.kayakmoscow.ru/sitemap.xml`.
- `og:url`, `og:image` — на www.
- 301 редирект apex → www работает.

То есть SEO-канонизация в порядке, и Яндекс **должен** в итоге перестроить индекс на www-варианты. Главное зеркало в Я.Вебмастере ускорит этот процесс.

### Доступ к ISPmanager

URL: `https://212.57.115.253:1500/ispmgr`. Логин `kayaking`, **пароль SSH** (FTP-пароль не подходит). Auth через POST API:

```bash
curl -sk -X POST "https://212.57.115.253:1500/ispmgr" \
  --data-urlencode "func=auth" --data-urlencode "out=json" \
  --data-urlencode "username=kayaking" --data-urlencode "password=<SSH>"
```

Session ID лежит в `doc.auth.$id`. Уровень доступа `16` (не root) — менять nginx-шаблон через панель **нельзя**, можно только переключать предопределённые поля (`hsts`, `redirect_www`, `redirect_http`, `php_mode` и т.д.).

`redirect_www` принимает только: `off_www` / `to_www` / `from_www`. **Объединённой опции «to_www_https» нет** — это и есть причина, почему цепочку редиректов нельзя упростить через панель.

### Что НЕ помогает в этой ситуации

- ❌ **Cloudflare** — не лечит проблему. Если apex заблокирован по hostname (SNI/Host), переход на CF-IP его не разблокирует (блок-то по имени).
- ❌ **Смена IP у хостера** — то же самое, проблема не в IP.
- ✅ Помогает только: убрать apex из маршрута пользователя (правильные ссылки в материалах, переиндексация Яндекса) и/или HSTS Preload (чтобы браузеры сами знали HTTPS+www).
