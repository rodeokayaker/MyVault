# Smart Kayak — roadmap by tracks

## Суть

Проект уже не на стадии голой идеи. Сейчас есть:
- прототип **SUP с E-Fin**;
- прототип **Kayak с водомётом**;
- тестовый контур ПО;
- подняты калибровка, BLE-соединение, командный протокол и протокол данных.

Главная задача следующего этапа — перестать быть набором работающих кусков и стать управляемой продуктовой системой. Ближайший центр тяжести — **предпродакшен SUP**. Каяк пока остаётся вторым треком.

## Текущее состояние

### Уже сделано
- [x] Есть prototype-grade SUP с E-Fin
- [x] Есть prototype-grade kayak с водомётом
- [x] ПО собрано в тестовом варианте
- [x] Поднята калибровка
- [x] Работает BLE-соединение
- [x] Поднят командный протокол по BLE
- [x] Поднят протокол данных по BLE

### Ещё не доведено
- [ ] Управление с телефона
- [ ] Несколько вариантов предиктора
- [ ] Улучшение качества текущего предиктора
- [ ] Предпродакшен SUP
- [ ] Предпродакшен kayak

## Главный принцип ближайшего этапа

Не распыляться на «всё сразу». Сейчас нельзя одинаково глубоко вести SUP, kayak, Smart Paddle, analytics и платформенность. На этом этапе нужен явный приоритет:

1. **SUP как первый product track**
2. **Smart Paddle / BLE / predictor как enabling stack**
3. **Kayak как второй, более тяжёлый трек**

## Track 1 — SUP / preproduction

### Цель
Собрать не просто рабочий прототип, а **предпродакшен SUP**, который:
- стабильно едет;
- управляется без головоломки;
- не стыдно показывать людям;
- уже можно использовать в demo / pilot / early product validation.

### Приоритетные задачи
- [ ] Зафиксировать целевую конструкцию предпродакшен SUP
- [ ] Доделать E-Fin как повторяемый и сервисный узел
- [ ] Доделать throttle / управление тягой
- [ ] Доделать логику кнопки и RGB LED
- [ ] Доделать управление с телефона
- [ ] Проверить onboarding первого использования: включение, pairing, старт, stop, safe mode
- [ ] Проверить герметичность, сервисность и заменяемость ключевых узлов
- [ ] Определить MVP-конфигурацию, которую можно нести в demo/pilot

### Критерий готовности трека
SUP готов к следующей фазе, когда им можно пользоваться не как лабораторной сборкой, а как первым product demo с внятным UX.

## Track 2 — Firmware / control / predictor

### Цель
Сделать управляющее ПО не просто рабочим, а предсказуемым, тестируемым и пригодным для сравнения алгоритмов.

### Приоритетные задачи
- [ ] Сформулировать 2–3 явных варианта предиктора
- [ ] Сравнивать предикторы не по вкусу, а по понятным KPI
- [ ] Довести текущий предиктор: снизить ложные и слабые срабатывания
- [ ] Развести production-логику и debug/experimental режимы
- [ ] Собрать минимальную тестовую матрицу: bench / simulation / water
- [ ] Зафиксировать критерии включения и выключения assist / predictive mode
- [ ] Привязать логи к разбору реальных заездов

### Практическая мысль
Сейчас предиктор «работает средне» — это честное и полезное состояние. Его нельзя прикрывать красивыми словами. Нужна не вера в алгоритм, а сравнимые версии и дисциплина проверки.

## Track 3 — Mobile control

### Цель
Сделать телефон не декоративным аксессуаром, а нормальным интерфейсом управления и настройки.

### Первая версия должна уметь
- [ ] подключаться к устройству по BLE
- [ ] показывать базовый статус
- [ ] менять режимы / параметры в разумных пределах
- [ ] запускать ключевые команды
- [ ] поддерживать калибровку и базовые сервисные действия
- [ ] быть достаточно простой, чтобы не ломать первый опыт

### Что не нужно пихать слишком рано
- сложную аналитику ради самой аналитики
- перегруженный dashboard
- десять режимов, которые никто не понимает

## Track 4 — Smart Paddle / sensing stack

### Цель
Укрепить сенсорный слой, потому что без него верхний интеллект будет стоять на песке.

### Приоритетные задачи
- [ ] Зафиксировать процедуру калибровки IMU
- [ ] Зафиксировать процедуру калибровки force sensing
- [ ] Описать BLE-контракт по каналам и полям
- [ ] Зафиксировать требования к качеству сигналов до water-test
- [ ] Увязать paddle-данные, predictor и логи в одну диагностическую цепочку

## Track 5 — Kayak

### Цель
Не замораживать kayak, но и не делать вид, что он сейчас главный product track.

### Приоритетные задачи
- [ ] Держать kayak как второй инженерный трек
- [ ] Проверить, что текущая силовая сборка не упирается в фундаментальное несоответствие водомёту
- [ ] Зафиксировать utility-сценарии, в которых kayak реально выигрывает
- [ ] Подготовить отдельный roadmap-переход: когда kayak станет следующим продуктовым фокусом

### Принцип
Kayak пока не надо доводить до той же стадии, что SUP. Иначе проект просто разорвётся.

## Рекомендуемая последовательность работ

### Фаза 1 — собрать продуктовый каркас SUP
1. Управление с телефона
2. Базовый throttle / UX управления
3. Кнопка / LED / safe mode
4. MVP-конфигурация предпродакшен SUP

### Фаза 2 — усилить control stack
1. 2–3 версии предиктора
2. Понятные KPI сравнения
3. Улучшение текущего варианта
4. Связка логов с реальными water-test результатами

### Фаза 3 — довести sensing discipline
1. Калибровки
2. BLE protocol contract
3. Качество сигналов
4. Тестовая дисциплина

### Фаза 4 — только потом расширять kayak
1. Актуализировать силовую конфигурацию
2. Выделить kayak-specific product thesis
3. Решить, когда он становится следующим главным треком

## Ближайшие 5 главных решений

- [ ] Каким должен быть первый UX телефона: только control/service или сразу quasi-dashboard?
- [ ] Какие именно 2–3 predictor variants сравниваем первыми?
- [ ] Что считаем критерием «предпродакшен SUP готов»?
- [ ] Какой минимальный набор safety / onboarding нужен для demo-grade product?
- [ ] Что сознательно НЕ делаем сейчас, чтобы не размыть фокус?

## Execution board

### NOW

То, что должно реально ехать первым фронтом, а не числиться в благих намерениях.

- [ ] Довести предпродакшен SUP до demo/pilot-ready состояния
- [ ] Сделать первую рабочую версию phone control
- [ ] Определить 2–3 predictor variants для сравнения
- [ ] Ввести KPI сравнения предикторов и water-test критерии
- [ ] Довести базовый UX: старт, stop, pairing, safe mode

### NEXT

То, что нужно сразу после стабилизации первого контура.

- [ ] Укрепить Smart Paddle sensing discipline
- [ ] Связать логи, predictor и реальные water-test сценарии
- [ ] Довести сервисность SUP-узлов
- [ ] Уточнить production-like конфигурацию control stack

### LATER

То, что имеет смысл, но не должно съедать фокус сейчас.

- [ ] Углублять kayak как следующий product track
- [ ] Расширять аналитику и richer dashboard
- [ ] Расширять линейку режимов и advanced behaviors
- [ ] Двигаться в OEM / licensing слой

### NOT NOW

То, что сейчас опасно делать слишком рано, даже если оно intellectually attractive.

- [ ] Пытаться одинаково активно тащить SUP и kayak как два главных продукта сразу
- [ ] Раздувать мобильное приложение до перегруженного control center
- [ ] Уходить в analytics-first продукт вместо assist-first продукта
- [ ] Полировать платформенность раньше, чем собран первый сильный product track

## Короткий вердикт

Сейчас зрелый ход такой:
- **доделать предпродакшен SUP**;
- **сделать телефон и управление внятными**;
- **поставить predictor development на рельсы сравнения, а не интуиции**;
- **kayak держать живым, но вторым**.

Иначе получится не roadmap, а нервное метание между несколькими полуправдами сразу.
