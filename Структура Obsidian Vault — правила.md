# Структура Obsidian Vault — правила

Цель: единая логика хранения заметок, чтобы не плодить дубликаты и не класть активное в архив.

## Базовая схема папок

### `00_Inbox/`
**Входящие**: черновики, быстрые заметки, планы созвонов/встреч, то, что ещё не разобрано.
- После обработки либо остаётся как артефакт встречи, либо переезжает в проект/area.

### `Daily/`
**Ежедневники**: задачи/фокус дня, быстрые заметки, done.
- В Daily допускаются ссылки на проекты/areas/ресурсы.
- Если в Daily появляется новая сущность (локация/человек/тема) — лучше создать для неё отдельную заметку в правильном месте и линковать уже туда.

### `01_Projects/`
**Проекты** (имеют цель/результат, дедлайны, активные deliverables).
Примеры:
- `01_Projects/Smart Kayak/` — всё по Smart Kayak (в т.ч. `Patent/`, `Hardware/` и т.п.)
- `01_Projects/Kayak Moscow/` — всё по бизнесу KayakMoscow (маркетинг, локации и т.д.)

Правило: материалы проекта (презентации, заявки, чертежи, маркетинг) — лежат внутри папки проекта.

### `02_Areas/`
**Сферы ответственности / личное** (долгоживущие темы без явного «конца»).
- `02_Areas/Personal/` — личные задачи/люди/быт/логистика (BMX, отправки, нотариусы и т.п.)

Правило: активное личное — в `02_Areas/Personal/`, не в архив.

### `03_Resources/`
**Справочники/чеклисты/инструкции** (то, к чему возвращаемся многократно).
Примеры:
- `03_Resources/Finance/…` — финансы/крипта/процедуры
- Документация/рукбуки/гайдлайны

Правило: если заметка — это «как делать X» или «чеклист», это ресурс.

### `04_Archive/`
**Архив**: завершённое/историческое, больше неактуальное.
Правило: сюда уезжают только закрытые задачи/проекты/устаревшие версии.

### `90_Templates/`
**Шаблоны**.

## Правила линков и именования

### 1) Избегать двусмысленных ссылок
- Не использовать голые ссылки вроде `[[Project]]`, если есть несколько файлов `Project.md`.
- Лучше ссылаться явным путём: `[[01_Projects/Smart Kayak/Project|Project]]`.

### 2) Точка входа в проект
- У проекта должна быть «корневая» заметка с понятным названием.
  - Например: `01_Projects/Kayak Moscow/KayakMoscow.md`.

### 3) Локации/контексты проекта
- Локации проекта (Строгино/Архангельское/СберСити) живут внутри проекта:
  - `01_Projects/Kayak Moscow/Locations/…`

### 4) Редиректы допустимы
- Если в Daily/истории уже есть ссылка на общее имя, можно делать «заметку-указатель» в корне, которая ведёт на актуальное место.

## Быстрый выбор «куда положить новую заметку»
- Это **созвон/черновик/ещё не разобрано** → `00_Inbox/`
- Это **план дня/задачи сегодня** → `Daily/`
- Это **часть проекта с результатом** → `01_Projects/<Project>/…`
- Это **личное/быт/люди/долгие обязанности** → `02_Areas/Personal/…`
- Это **инструкция/чеклист/справочник** → `03_Resources/…`
- Это **уже не нужно активно** → `04_Archive/`

## Как правильно заполнять vault на практике

Ниже — не теория, а рабочие правила по живым паттернам этого vault.

### 1) У каждого проекта должна быть одна настоящая точка входа
- В папке проекта должна быть одна главная заметка `Project.md` или другая явно корневая заметка.
- Все поднаправления (`SUP`, `Kayak`, `Smart Paddle`, `Patent`, `Hardware`) должны ссылаться на неё.
- Если есть заметка-синоним вроде `Smart Kayak.md`, пусть она будет коротким редиректом на `Project.md`, а не вторым центром проекта.

### 2) Не смешивать роли заметки
Если заметка одновременно пытается быть:
- индексом,
- рабочей спецификацией,
- архивом исходника,
- backlog’ом,

то это уже плохая заметка.

Нормально разделять роли так:
- `Project.md` / `SUP.md` — индекс и управленческая рамка;
- `docs/...` — рабочие тематические заметки;
- `Исходный документ ...` или обзорная заметка — source/archive слой;
- `Next actions` — короткий список решений и ближайших шагов, а не свалка всего подряд.

### 3) Сначала сохранить источник, потом разносить знание
Если приходит внешний документ, PDF, черновик, ТЗ или чужой markdown:
1. сохранить его как отдельную source note внутри проекта;
2. привести к читаемому виду;
3. вынести из него рабочие заметки по темам;
4. связать всё через index note.

То есть не запихивать всё в одну простыню и не терять происхождение материала.

### 4) Большие проектные темы дробить по функциям, а не по настроению
Хорошее дробление:
- архитектура;
- батарея;
- контрол-бокс;
- motor dock;
- E-Fin;
- исследование рынка;
- патент;
- дизайн;
- backlog.

Плохое дробление:
- `идеи 2`, `новое`, `разное`, `наброски final`, `мысли по проекту`.

Имя заметки должно отвечать на вопрос: **зачем я открою её через месяц?**

### 5) Index note должна вести, а не дублировать всё
В `Project.md` или `SUP.md` нужны:
- `Goal`
- `Scope`
- `Docs` / ключевые материалы
- `Next actions`
- связи с поднаправлениями

Там не нужен полный пересказ всех дочерних заметок. Индекс должен вести по структуре, а не заменять её.

### 6) Next actions — только про решения и движение
В `Next actions` держать:
- открытые развилки;
- ближайшие инженерные шаги;
- проверки;
- решения, которые реально тормозят проект.

Не держать там:
- исторический done-log;
- все мысли подряд;
- дальние фантазии без срока и смысла.

Если список начинает пухнуть — выносить backlog в отдельную заметку проекта.

### 7) Явные ссылки лучше красивой двусмысленности
Для этого vault правильнее:
- `[[01_Projects/Smart Kayak/Project|Project]]`
- `[[01_Projects/Smart Kayak/SUP/SUP|SUP]]`

чем:
- `[[Project]]`
- `[[Architecture]]`

Короткая ссылка красива ровно до первого дубля. Потом это уже не красота, а грязь.

### 8) Отдельно хранить обзор, отдельно — рабочее мясо
Если заметка нужна как обзор для человека — пусть будет обзорной.
Если заметка нужна как инженерный рабочий узел — пусть будет узкой и предметной.

Пример хорошего слоя:
- `SUP.md` — куда смотреть;
- `SUP — системная архитектура.md` — как это устроено;
- `SUP — E-Fin.md` — отдельная предметная зона;
- `Электро-САП борд — Техническое описание.md` — исходник/обзор.

### 9) Resources — не склад всего полезного, а слой повторного использования
В `03_Resources/` класть только то, к чему есть смысл возвращаться многократно:
- правила;
- чеклисты;
- инструкции;
- справочники;
- шаблоны мышления или процедур.

Если заметка существует только внутри одного проекта, ей почти всегда место внутри проекта, а не в Resources.

### 10) Daily не должен становиться чёрной дырой
В Daily можно быстро фиксировать мысли и задачи. Но если там возникло что-то содержательное:
- тема,
- человек,
- проектная идея,
- решение,
- артефакт,

то это нужно вынести в отдельную заметку и оставить в Daily ссылку, а не хоронить смысл в дневнике.

### 11) Именование должно быть человеческим и долговечным
Хорошо:
- `Батарея SUP — спецификация`
- `SUP — Motor Dock`
- `Практическое исследование — продукт, кастдев, KPI`

Плохо:
- `новая версия`
- `мысли`
- `заметки по созвону 2`
- `draft final final`

Название должно переживать контекст текущей недели.

### 12) Архив — это конец активности, а не чулан неловкости
В `04_Archive/` переносить только то, что:
- завершено,
- больше не ведётся,
- не участвует в активной системе ссылок.

Не архивировать просто потому, что заметка выглядит старой. Если она всё ещё опорная — она живая.

## Практический стандарт для проектной заметки

Минимальный хороший каркас:
- frontmatter (`type`, `status`, `tags`, `updated`)
- `# Название`
- `Goal`
- `Scope` или `Context`
- `Docs` / ключевые материалы
- `Next actions`
- `Links` / `Связанные заметки`

Для тематической заметки:
- короткая `Суть`
- предметные разделы по теме
- открытые вопросы
- ссылки на родительский проект и соседние заметки
